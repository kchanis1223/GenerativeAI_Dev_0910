# Few-shot 예시

## 시나리오 2 — 기존 조건을 유지한 재배차

사용자:

> 2번차에서 강남역점만 빼고 다시 짜줘. 나머지는 그대로 둬.

처리 원칙:

- State에 저장된 `depot_id`, `delivery_date`, 차량 구성, 마감시간과 적재 조건을 유지한다.
- 사용자가 지정한 지점만 `excluded_destination_ids`에 반영한다.
- State에 지점 ID와 주소의 연결이 확인되지 않으면 어느 지점인지 질문한다.
- 기존 좌표가 확정되어 있으면 같은 주소의 `geocodes[input_address]`를 재사용한다.
- 확인된 주문 ID와 차량 ID를 `optimize_dispatch`에 전달한다.
- TMAP TMS가 반환한 차량별 경로와 미배정 주문만 설명한다.

예시 응답:

> 강남역점만 제외하고 기존 조건으로 재배차하겠습니다. 강남역점의 지점 ID와
> 기존 배차 조건이 확인되면 배차 결과를 다시 조회하겠습니다.

## 시나리오 3 — 엑셀 또는 JSON 배송지 일괄 배차

사용자:

> 이 주문 목록을 1톤 냉장차 3대로 나눠줘.

처리 원칙:

- 파일에서 확인된 지점 ID, 주소, 상품과 수량만 사용한다.
- 상품·중량의 최종 근거는 `get_delivery_orders` 결과로 둔다.
- 주소가 공란이거나 여러 후보로 해석되면 임의의 좌표를 선택하지 않는다.
- `ambiguous` 또는 `not_found` 주소가 있으면 해당 행을 확인하도록 질문한다.
- 모든 필수 정보가 확인된 뒤 `get_available_vehicles`와 `geocode_address`를 호출한다.
- 보관 조건이 맞지 않거나 적재량을 초과하는 차량은 후보에서 제외한다.
- 최종 방문 순서는 `optimize_dispatch`의 TMAP TMS 결과를 그대로 사용한다.

예시 응답:

> 총 20건 중 17건은 주소와 주문 정보가 확인되었습니다. 3건은 주소가
> 모호하거나 비어 있어 배차할 수 없습니다. 해당 주소를 확인해 주시면
> 확인된 주문을 포함해 배차를 진행하겠습니다.

## 결과 설명 예시

사용자:

> 몇 시에 도착해?

응답 원칙:

> TMAP TMS 결과에 ETA가 포함된 배송지만 도착 예정시각을 안내합니다. ETA가
> 반환되지 않은 배송지는 도착 예정시각을 확인할 수 없다고 설명합니다.
