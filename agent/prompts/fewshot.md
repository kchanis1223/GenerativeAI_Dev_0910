# Few-shot 예시

## 시나리오 1 정상 배차

본사 물류 운영자:

> 노량진센터에서 2026년 9월 11일 마포·서대문·은평 지점 주문을 가용 차량으로 배차해줘.

처리 원칙:

- 서버 마스터에서 확인한 CENTER-NR, S01·S02·S03을 사용한다.
- `get_delivery_orders`로 해당 날짜와 지점의 주문을 조회한다.
- `get_available_vehicles`로 가용 차량을 조회한다. 임의로 차량 수를 정하지 않는다.
- 기존 `geocodes[input_address]`가 확정됐으면 재사용하고, 없으면 `geocode_address`로 확인한다.
- 보관 조건·적재량·확정 좌표를 검사한 주문과 차량만 `optimize_dispatch`에 전달한다.
- TMS의 `DispatchResult`를 화면이 직접 표시한다. 성공 여부나 ETA를 미리 약속하지 않는다.

## 시나리오 2 입력 보완

본사 물류 운영자:

> 마포지점으로 배차해줘.

서버에서 출발 센터와 지점은 확인됐지만 배송일이 없는 경우:

> 배송일을 알려주세요.

- `ambiguous` 또는 `not_found` 주소는 확정 주소를 요청하고 배차하지 않는다.
- 필수값 보완은 같은 요청 ID에서 이어간다. 다른 대화나 완료된 배차의 조건을 가져오지 않는다.

## 시나리오 3 실패와 미배정 안내

- 배차 결과 조회가 실패하면 실행 계층의 제한된 재시도 후 실패를 안내한다.
- 모델은 `optimize_dispatch`를 다시 호출해 새 배차를 만들지 않는다.
- 미배정 주문과 제공된 사유는 결과 화면에 그대로 표시한다.
- ETA가 없으면 정보 없음으로 표시한다. 임의의 도착시각을 만들지 않는다.
- 재배차·점주 업무·기사 대화·파일 업로드 요청에는 이번 지원 범위를 안내한다.
